# PRD Review：智能模型路由 (Intelligent Model Routing)

> **被评审文档**: `docs/01-requirements-product/PRD-intelligent-model-routing.md` v1.0  
> **评审日期**: 2026-06-21  
> **评审视角**: 产品经理  
> **评审人**: AI Agent  
> **结论**: 方向正确，建议补充数据基线、成本模型、用户控制感、隐私告知后进入设计评审

---

## 一、总体判断

该 PRD 准确识别了当前系统核心矛盾——Apple Silicon 48GB 统一内存无法支撑长 Agentic 会话，而云端 API 可作为长上下文的自然溢出通道。整体方向正确、边界清晰、向后兼容意识强。

但作为一份面向实施的产品需求文档，它在**数据可信度、用户控制感、隐私合规、成本模型、失败场景**等方面仍需补强，否则上线后容易因"用户不信任自动切云"而翻车。

---

## 二、肯定点

### 2.1 定位与边界清晰

- 明确提出"不替代 LiteLLM、不引入第三方依赖、不做语义路由"，有效控制了产品范围。
- "同一 Session 内不反复切换"是正确决策，避免了后端 ping-pong 导致的上下文漂移与模型行为不一致。

### 2.2 用户故事贴近真实场景

- US-1 长会话自动保护、US-2 新会话回本地、US-5 强制本地模式均命中目标用户（Apple Silicon + Claude Code 开发者）的真实痛点。

### 2.3 可观测性设计周全

- 路由状态进入 `/status`、metrics 进入 JSONL、成本估算三层覆盖，便于后续诊断和调优。

### 2.4 向后兼容意识强

- `PROXY_ROUTE_ENABLED=false` 默认关闭，现有纯本地用户不受影响，降低了引入风险。

---

## 三、主要问题与改进建议

### 3.1 核心数据假设缺乏验证

| 问题 | 当前表述 | 风险 | 建议 |
|---|---|---|---|
| 本地请求占比 | "87% 请求保留本地，13% 传云端" | 数字无来源，无法验证 | 补充测算依据：基于多少 sessions、多长上下文、什么任务类型 |
| 月度成本 | "¥5-34 (flash)" | 依赖未经验证的路由率和 token 假设 | 给出计算公式：日均请求数 × 路由率 × 平均 input/output tokens × 单价 |
| 循环注入率 | "路由部分降至 <1%" | 承诺过于绝对，验收困难 | 改为"目标下降"或"需实验验证"，避免无法验收 |

**建议**: 在 PRD 中新增"数据基线附录"，标注所有指标的采样时间、样本量和计算方式。

---

### 3.2 用户控制感不足

当前设计是"系统自动决策、Session 内保持"，这对系统稳定性有利，但削弱了用户感知和干预能力：

- 用户不知道"为什么这次走了云端"
- 用户无法在单次请求级别覆盖路由
- `/status` 只能看，不能操作

**建议补充需求**:

| 需求 | 优先级 | 说明 |
|---|---|---|
| 路由事件主动通知 | P1 | 首次路由到云端时，在日志或 `/status` 顶部显示提示及原因 |
| 单次请求覆盖机制 | P2 | 通过 header 如 `X-Proxy-Route-To: local/cloud` 强制指定后端 |
| 一键切回本地 | P2 | `/status` 提供手动标记当前 session 为 `local_only` 的入口 |

---

### 3.3 Session 一致性与模型行为差异

PRD 要求"同一 Session 内不切换后端"，但未说明：

- 如果云端 Session 中遇到明显短上下文任务，是否仍走云端？
- DeepSeek 与 Qwen 输出风格差异是否会让用户困惑？

**建议**: 在 FR-1.3 中明确"Session 级一致性优先于单次请求优化"，并考虑在切换时给出用户提示。

---

### 3.4 成本估算精度不足

FR-4.4 提出基于 DeepSeek 公开定价做成本估算，但未解决：

- output tokens 在请求前未知，如何估算？
- 是否按 `max_tokens` 上限估算最坏成本？
- 不同 cloud model 价格不同，是否配置化？

**建议**:

- 区分 **pre-request 估算**（input tokens + `max_tokens` 上限）和 **post-request 真实成本**（实际 usage）
- 新增配置 `PROXY_CLOUD_PRICE_INPUT`、`PROXY_CLOUD_PRICE_OUTPUT`，避免硬编码

---

### 3.5 隐私合规表述薄弱

虽然 US-5 有强制本地模式，但整体对隐私的交代偏轻：

- 代码/文件内容上传云端是否合规？
- 首次启用时是否明确告知用户？

**建议补充**:

- 在"产品边界"或 NFR 中增加隐私声明要求
- 首次启用路由时，在日志/status 输出警告："请求将发送至云端 API：{cloud_base_url}"
- 可考虑敏感文件路径/关键词黑名单（P2），避免特定内容上传

---

### 3.6 回退策略有潜在死锁风险

FR-2.3/2.4 规定云端失败回退到本地，但存在以下风险：

- 如果触发路由的原因正是本地上下文太长，回退到本地仍会 OOM
- 连续 3 次失败后永久标记 `local_only`，该 Session 可能被"判死刑"

**建议**:

- 回退到本地时，若触发原因是大上下文，应同时触发激进的本地截断，并告知用户
- 或提供"重试云端"逃生通道，避免永久 `local_only`

---

### 3.7 缺少 A/B 实验与验收指标

PRD 提到"下次评审：Phase 1 MVP 完成后"，但未定义 Phase 1 验收标准。

**建议增加**

| 阶段 | 验收指标 | 数据来源 |
|---|---|---|
| Phase 1 MVP | 路由触发准确率 ≥ 95%（不过度路由、不漏路由） | `proxy_metrics.jsonl` |
| Phase 1 MVP | 云端请求占比在预期范围（如 10–20%） | metrics |
| Phase 1 MVP | 路由不引入新的 500 错误 | metrics |
| Phase 2 | 用户手动覆盖使用率 | 日志统计 |
| Phase 2 | 月度实际成本 vs 预估偏差 < 30% | 账单对比 |

---

## 四、优先级调整建议

| 当前 PRD 内容 | 当前优先级 | 建议调整 | 理由 |
|---|---|---|---|
| FR-1.4 内存压力触发路由 | P1 | **提升为 P0** | 长上下文往往伴随高内存，仅按 chars 路由可能不及时 |
| FR-4.4 成本估算 | P2 | **提升为 P1** | 成本是用户最敏感点，缺失会导致上线后信任崩塌 |
| FR-2.3/2.4 云端回退 | P1 | 保持 P1 | 但需明确"大上下文回退本地"时的降级策略 |
| US-3 成本感知 | P1 | 保持 P1 | 建议增加"首次路由时提示估算费用"的验收标准 |

---

## 五、需要补全的内容清单

1. **数据基线附录**: 当前 9% 循环注入率、21.6% 上下文丢失、28s TTFT 的数据来源和采样时间
2. **成本模型附录**: 月度 ¥5-34 的详细计算公式与假设
3. **隐私与合规章节**: 明确哪些数据会离开本机、如何脱敏、用户如何拒绝
4. **用户旅程图**: 首次启用路由 → 第一次触发 → 切换 → 回退 → 新 Session 的完整流程
5. **失败场景清单**: 除云端不可用外，覆盖本地不可用、两边都不可用、API key 失效等场景
6. **路由决策示例表**: 用具体 chars/stage/memory 组合说明最终路由结果

---

## 六、最终结论

该 PRD 在**技术方向和产品定位**上是正确的，智能路由确实是解决 48GB 长会话瓶颈的最优雅路径之一。但作为产品文档，它目前更像"技术方案概要"。

> **最关键的三个补强点：可信的成本模型、清晰的用户控制感、完善的隐私告知。**

如果这三点补齐，并补充数据基线附录与失败场景清单，该 PRD 可直接进入设计文档编写阶段。

---

## 七、建议下一步

1. 作者补充"数据基线附录"和"成本模型附录"
2. 增加"用户控制"章节（单次覆盖、手动切回、首次通知）
3. 增加"隐私与合规"章节
4. 明确 Phase 1 MVP 验收指标
5. 重新评审后进入 `docs/02-architecture-design/intelligent-model-routing-design.md` 编写
