## 2. 逐变量相关性分析

### 2.1 窗口深度 KEEP 24→80 —— **强相关（判定实验级证据）**

- 机制：fifo 按消息条数截断，24 条 ≈ 11-12 轮开始丢早期探索积累；35B 需 ~22 轮进入写 patch 阶段。
- 正向证据：KEEP80 后立即产出 4054B（09-03 17:03，其余条件不变仅改窗口）。
- 反向证据链：KEEP24 时代产出**不稳定**——08-16 成、08-25 败、08-27 时成时败、09-01 171 请求仍 0B（大量 rabbit_hole 重读：上下文丢失 → 重读 → 再丢失的循环）。**同配置时好时坏正是"边界资源"的特征**：探索路径恰好未越过窗口边界时能成，越过即败。
- 结论：KEEP24 下产出是**运气**，KEEP80 是**使能条件**。单实例 N=1，方向性强、幅度未定。

### 2.2 ctx_engine on/off —— **两段论：与窗口无关，与 aux 污染强相关**

- 09-03 的 engine-off 对照同样 0B → 引擎本身不是 09-03 失败的原因（排除链第一条）。
- 09-04 复现：engine-on + 新盐 + KEEP80 → **2 请求即 exit=0（假完成）**——aux 共键污染 canonical → 主对话 400 → 会话早死。修复（::aux-haiku 分域）后**无一次有效验证**（23:00 验证被 probe 429 中止）。
- 结论：**engine-on 在干净环境下从未被验证过一次完整会话**。生产现值 engine-on 属于"已修未证"状态；重启窗口后的首个自然长会话是它的判定实验。

### 2.3 压缩栈层数 —— **中等强度负相关（信息税）**

同为 engine-off + KEEP80：透传（全关）5822B > 压缩 on 4054B；且透传跑出 98.5% 前缀命中、15s/轮、51 轮收敛、13 次 Edit。机制上每层改写（压缩/摘要/清除）都是一次信息税 + 前缀断裂源。但样本单向（无"透传失败"反例），且透传的 OOM 风险只是没被触发（512KB 内）。**方向可信，幅度未证**。

### 2.4 会话新鲜度（SWE_SESSION_SALT）—— **强相关（唯一变量对照）**

09-04 23:25-23:52 三次透传 0B（旧盐残留 → 引擎期污染历史 → "任务已完成"错觉/路径死循环）→ 换新盐唯一变量变化 → 5822B。同时 08-27 14:45（5171B 次日复跑 0B）疑似同因。**结论：跨配置复用 session 是隐性强干扰源，任何对照实验必须新盐**。

### 2.5 轮预算 —— **必要条件（强）**

透传 100 轮预算下实际 51 轮收敛；旧配置 25 轮上限必然截断收敛过程（09-02 的 51 轮慢跑在 25 轮预算下不可能完成）。与 2.1 叠加构成"探索积累期"的两侧：**窗口决定记得多少，预算决定能走多远**。

### 2.6 模型 —— **能力底座（中等）**

同窗口（KEEP80）同条件：35B 产出 4054B，27B 0B（26 请求正常探索但无产出，压缩变量未隔离）。35B 批跑 exit 率 95%（40/42）。27B 失败至少部分归因 aggressive 压缩（confound 未隔离），不能全记模型能力。**分层结论：模型能力是底座，上下文管理是使能层——底座不够时使能层无从谈起**。

### 2.7 后端缓存/驱逐 —— **与延迟强相关、与成败弱相关**

驱逐死循环（52K/轮请求触发 517 次驱逐，4-14 min/轮）拖慢但未直接导致 0B（09-02 的 194s/轮慢跑仍产出 2872B）；98.5% 命中 → 15s/轮。**缓存治理是性能问题，不是成败问题**——但慢死会耗尽预算/耐心（exit=143 超时一次）。

### 2.8 ctx_recall —— **与结果零相关（零触发）**

四次真实会话零调用，模型用重读替代（可再生内容）。召回链路的机械可用性已由 L1 案例证实（TC06-10/21a 全绿），行为触发待 B-suite。**当前生产结果不依赖 ctx_recall**。

## 3. 定性结论（按证据强度排序）

1. **【强】探索积累的连续性是 35B 产出 patch 的必要条件**——窗口深度（KEEP≥80）× 轮预算（≥50）× 会话新鲜度三者任一破坏都会以 0B 告终，三者构成"上下文管理的下限条件组"。
2. **【强】ctx_engine 的失败记录全部由 aux 共键污染解释，引擎折叠机制本身未败未证**——"已修未证"是当前最大悬案，判定实验 = 重启后首个自然长会话。
3. **【中】压缩/截断栈存在可测的信息税**——透传 > 单层压缩 > 多层，每层都有代价；但"透传最优"不能外推为生产建议（OOM 未触发 ≠ 安全），正确方向是"少而准的压缩"（写入期压缩 + 可寻址登记）。
4. **【中】模型能力与上下文管理是乘法关系**——27B 在同条件下无产出说明使能层有底座要求；35B 在坏条件下也归零说明底座不能替代使能层。
5. **【弱/方向性】缓存治理影响时间成本不影响成败**——但会通过超时间接致败。
6. **【观察】ctx_recall 在当前生产流量中贡献为零**——其价值场景（不可再生的折叠内容）尚无真实样本。

## 4. 混淆与局限（结论可信度边界）

- **N=1 实例纵向**：全部因果方向来自单实例 24 次 run；批跑横截面因 eval 口径混杂无法按配置切分。
- **多变量共变**：08-16→08-27 换了模型（Qwen3.6→ornith）；09-03 17:03 同时改回 engine off + KEEP80。严格说只有三组"单变量对照"成立：窗口（09-03 17:03）、盐（09-04 23:52→23:41）、引擎复现（09-04 22:21）。
- **exit ≠ resolved**：5171B/4054B/5822B 均**未 resolved**（评测未过）——本分析的相关性是"产出行为"（有无 patch、大小、轮次）与条件的相关，不是"解题正确性"的相关。resolved 率与条件的相关需要批跑级 controlled A/B（swe-eval 侧尚无）。
- **proxy_verify 请求数是代理侧口径**，agent 侧真实轮次另计。

## 5. 后续验证路径（按信息增益排序）

1. engine-on + aux 修复的首个自然长会话（同时回答 §2.2 悬案与 D 分支判定）；
2. KEEP80 + 压缩 on 的复跑稳定性（≥3 次同条件，检验 4054B 的可重复性——KEEP24 的"时好时坏"是否消失）；
3. 透传与压缩 on 的批跑 A/B（≥10 实例受控对照，把 2.3 从单向样本升级为统计结论）；
4. 27B 去掉 aggressive 压缩的单例复跑（隔离模型变量与压缩变量）。
